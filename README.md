# promo_draw

Сайт и личный кабинет для промо-акции «10 месяцев побед» (мороженое
«Эскимос»): регистрация участников, ввод промокода с палочки под защитой от
подбора, ежемесячные розыгрыши призов плюс годовой супер-розыгрыш,
email-уведомления и массовая загрузка промокодов через админку.

Продакшн: https://promo-draw.duckdns.org

## Возможности

### Публичный сайт

- Главная страница: обратный отсчёт до ближайшего розыгрыша (9-е число,
  21:00 по Москве — момент один и тот же для всех посетителей независимо от
  часового пояса браузера, считается на сервере; после конца акции блок
  пропадает), разбор «как получить шанс на победу» в 3 шага, список
  товаров-участников акции, призовой фонд (ежемесячный и супер-розыгрыш),
  правила акции со ссылкой на PDF, блок «какие данные нужны победителю»,
  FAQ на 6 вопросов (общий источник текста с личным кабинетом).
- Блок победителей по месяцам прямо на главной: имя в формате «Имя Ф.»,
  код, телефон в маскированном виде (видны только последние 4 цифры), приз.
  По умолчанию открыта вкладка последнего прошедшего месяца. Пункт
  «Победители» в шапке — якорная ссылка на этот блок, а не отдельная
  страница.
- Шапка с меню, логотипом и входом в ЛК остаётся на экране при прокрутке
  страницы.
- Статичные страницы (о нас, контакты, акции, персональные данные,
  пользовательское соглашение, правила и условия лояльности, реквизиты
  организатора, cookie-политика) — пока заглушки с текстом «появится здесь
  позже», ждут реального наполнения.

### Личный кабинет

- Регистрация и вход по email (без учёта регистра — `Ivan@mail.ru` и
  `ivan@mail.ru` один и тот же аккаунт), подтверждение почты по ссылке
  (с кнопкой «отправить письмо ещё раз», если не подтвердил, не чаще раза
  в минуту), сброс и смена пароля.
- Вход защищён от подбора пароля: 5 неудачных попыток за 5 минут по связке
  email+IP — блокировка с растущей задержкой (от 5 минут, максимум час).
  Чекбокс «Запомнить на этом устройстве» управляет временем жизни сессии.
  Уже вошедшего пользователя со страниц входа и регистрации сразу
  перенаправляет в кабинет.
- Профиль: ФИО, дата рождения, телефон, адрес доставки приза, переключатель
  письма о регистрации промокода. Ввод промокода заблокирован баннером с
  понятной причиной, пока не подтверждена почта и не заполнен профиль
  (имя, фамилия, дата рождения, телефон).
- Ввод промокода с разными сообщениями на каждый случай: код не найден, код
  уже использован кем-то другим, свой же код введён повторно (без штрафа),
  не подтверждена почта, не заполнен профиль, акция ещё не началась или уже
  завершена, идёт подведение итогов периода (с 21:00 9-го числа до полуночи
  коды на новый период не принимаются), временная блокировка — с обратным
  отсчётом до её окончания.
- Защита от подбора кода: 3 неудачные попытки за минуту — блокировка ввода
  промокода на 5 минут. Успешное погашение сбрасывает счётчик, остальной ЛК
  при блокировке доступен.
- «Мои коды» — история введённых кодов со статусами (ожидание /
  выиграл / без выигрыша) и счётчиками по каждому статусу.
- «Победители» — тот же виджет по месяцам, что и на главной странице.
- Публичный ID участника (не совпадает с внутренним ID в базе) — копируется
  по клику.

### Розыгрыши

- Акция идёт с 9 февраля по 31 декабря 2026 включительно — код нельзя
  погасить ни до старта, ни после конца акции.
- Ежемесячный розыгрыш: 10 штук, с марта по декабрь. Первый период стартует
  прямо с началом акции (9 февраля), дальше каждый период — с 10-го числа
  прошлого месяца по 9-е текущего включительно. Подводится автоматически
  каждое 9-е число в 21:00 по Москве (Celery Beat). Сейчас разыгрываются
  2 приза.
- Если авто-розыгрыш по какой-то причине не сработал вовремя, отдельная
  задача каждые 30 минут проверяет все периоды акции и дозакрывает
  пропущенные — без потери и задвоения билетов.
- Супер-розыгрыш — разовое событие 01.01.2027 в 00:00 по Москве, билеты за
  весь срок акции (09.02–31.12.2026 включительно), 4 приза. Победители
  ежемесячных розыгрышей не исключаются из супер-розыгрыша.
- Каждый погашенный за период код — отдельный билет: чем больше кодов
  погасил участник, тем выше шанс. Победитель выбирается криптографически
  случайным перемешиванием билетов и призов.
- Один и тот же человек может выиграть не больше раза в ежемесячных
  розыгрышах и не больше раза в супер-розыгрыше (максимум 2 приза за акцию).
- Ручной запуск подведения итогов из админки — безопасен даже если
  автоматическая задача уже отработала (не задвоит результат). Если
  активных призов не хватает на всех, розыгрыш всё равно закрывается, но
  и в лог, и в саму админку уходит предупреждение.
- Если аккаунт победителя позже удалят, запись о победе не исчезает — ФИО,
  email и телефон на момент выигрыша сохраняются отдельно от аккаунта.

### Уведомления

- Письмо для подтверждения почты, письмо для сброса пароля.
- Письмо «промокод зарегистрирован» — можно отключить в профиле.
- Письмо «вы выиграли» — обязательное, без отключения, называет конкретный
  розыгрыш и даёт ссылку в личный кабинет; при сбое отправки переотправляется
  отдельной периодической задачей — не больше `MAX_RESEND_ATTEMPTS` раз, после
  чего попытки прекращаются и победителя видно в админке по счётчику попыток.
- Сбой при постановке письма в очередь (например, недоступен Redis) не
  мешает самому действию — код всё равно засчитывается, письмо просто не
  уходит в моменте.

### Админка

- Пользователи — поиск по email/имени/телефону, фильтры по staff/активности/
  подтверждению почты; в карточке видны адрес доставки приза и согласие на
  рассылку.
- Промокоды — список с точным поиском по коду и поиском по email
  погасившего, фильтр по дате погашения; кнопка «Загрузить из xlsx»
  (проверка расширения, MIME-типа, лимит 10 МБ, что файл реально читается
  как xlsx, отсев дублей внутри файла и по базе, строка-заголовок таблицы
  распознаётся и пропускается, отчёт «обработано / добавлено / отклонено»
  с разбивкой по причине считается по факту вставки, а не заранее).
  Массовая генерация — командой `generate_promo_codes` (алфавит без
  символов, которые легко перепутать при переписывании с палочки: `O`/`0`,
  `I`/`1`, `S`/`5`).
- Журнал попыток погашения промокодов — доступен только для чтения, со
  статусом и причиной отказа по каждой попытке (пригодится для поддержки и
  разбора спорных случаев); повторные попытки во время блокировки его не
  засоряют. Старые записи можно вычищать командой `clean_old_attempts`.
- Призы и розыгрыши — отдельные пулы призов на ежемесячный и супер-розыгрыш
  (можно временно отключать призы флагом `is_active`), действие «Определить
  победителя вручную» на розыгрыше — если активных призов не хватит на
  всех, админка честно предупредит об этом.
- Победители — список только для чтения: кто определил победителя (авто или
  вручную и кем), когда отправлено письмо. ФИО, email и телефон сохранены
  отдельным снимком на момент выигрыша — не пропадают, даже если аккаунт
  победителя потом удалят.
- Дневная статистика (регистрации, успешные/неуспешные попытки погашения) с
  действием «Экспортировать в Excel».

## Стек

Python 3.12, Django 5.2, PostgreSQL, Redis, Celery + Celery Beat
(`django-celery-beat`), gunicorn, nginx, Docker Compose.

## Требования

- Python 3.12 — для запуска без Docker.
- Docker и Docker Compose — для запуска через контейнеры (рекомендуемый способ).
- PostgreSQL и Redis — поднимаются автоматически через Docker Compose; для
  запуска без Docker нужны установленными отдельно.

## Переменные окружения

Перед первым запуском скопируйте `.env.example` в `.env` и подставьте реальные
значения:

```
cp .env.example .env
```

- `SECRET_KEY` — обязателен, без значения по умолчанию. Сгенерировать новый:
  `python -c "import secrets; print(secrets.token_urlsafe(50))"`.
- `DEBUG` — `True` только для локальной разработки, на боевом сервере `False`.
- `ALLOWED_HOSTS` — домены/IP через запятую, без пробелов.
- `CSRF_TRUSTED_ORIGINS` — домены со схемой (`https://example.com`), через
  запятую; нужен только когда сайт открыт по HTTPS через nginx.
- `SITE_URL` — домен сайта для ссылок в письмах, без слэша на конце.
- `CELERY_BROKER_URL` / `REDIS_CACHE_URL` — адреса Redis для брокера Celery и
  для кэша соответственно (разные базы одного Redis). Через Docker Compose
  переопределяются на `redis://redis:6379/...` прямо в `docker-compose.yml`,
  значения из `.env` для контейнеров не используются.
- `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` — обязательны, без
  значений по умолчанию. `POSTGRES_HOST` / `POSTGRES_PORT` при запуске через
  Docker Compose тоже переопределяются в `docker-compose.yml`.
- `EMAIL_HOST` / `EMAIL_PORT` / `EMAIL_HOST_USER` / `EMAIL_HOST_PASSWORD` /
  `EMAIL_USE_TLS` — настройки SMTP. При `DEBUG=True` не используются, письма
  выводятся в консоль. Если провайдер блокирует исходящие 587/465 (частая
  практика у VDS-хостеров), стоит попробовать порт 2525 — большинство
  почтовых сервисов держат его как раз на такой случай.
- `DEFAULT_FROM_EMAIL` — адрес отправителя.

## Локальный запуск без Docker

```bash
python -m venv venv
source venv/Scripts/activate  # Windows: venv\Scripts\activate
pip install -r requirements-dev.txt

cp .env.example .env  # и подставить значения
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Для Celery (в отдельных терминалах, нужны запущенные Postgres и Redis):

```bash
celery -A promo_draw worker --loglevel=info --pool=solo
celery -A promo_draw beat --loglevel=info
```

## Запуск через Docker

Локально нужны оба файла — `docker-compose.local.yml` добавляет runserver и
публикацию портов Postgres/nginx для разработки. Он не подхватывается
автоматически, поэтому команда без флага `-f` на сервере поднимет
только продакшн-конфигурацию.

```bash
cp .env.example .env  # и подставить значения

docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
```

Сайт доступен на `http://localhost:8000/` (напрямую через runserver) и на
`http://localhost/` (через nginx).

## Управляющие команды

- `python manage.py generate_promo_codes --count N` — генерирует `N`
  промокодов пачками по 10 000 (`secrets.choice`, коллизии с уже
  существующими кодами пропускаются). Алфавит — заглавные латинские буквы и
  цифры без `O`, `I`, `S`, `0`, `1`, `5` (легко перепутать при переписывании
  с палочки от мороженого). Останавливается с ошибкой, если подряд 5 пачек
  не добавили ни одного нового кода — сигнал, что свободных 8-значных
  комбинаций почти не осталось.
- `python manage.py clean_old_attempts [--days N] [--dry-run]` — удаляет
  записи журнала попыток погашения старше `N` дней (по умолчанию 90). С
  `--dry-run` только показывает, сколько записей попадёт под удаление.

## Тесты

```bash
pytest
```

Тесты лежат в `tests/` на уровне проекта, а не по одному `tests.py` в каждом
приложении. `pytest-django` сам поднимает и удаляет отдельную тестовую базу.

## Ruff

Линтер и форматтер, конфиг — в `pyproject.toml` (`[tool.ruff]`): длина строки
80 символов, `target-version = "py312"`, миграции и `venv` исключены из
проверки. Включённые правила — `E`/`W` (pycodestyle), `F` (pyflakes), `I`
(сортировка импортов, замена isort).

```bash
ruff check .          # линтер
ruff check . --fix    # линтер с автофиксом того, что можно исправить безопасно
ruff format .         # форматирование (двойные кавычки)
ruff format --check . # проверить форматирование без изменения файлов
```

CI гоняет `ruff check .` и `ruff format --check .` — то есть падает и на
ошибках линтера, и на неотформатированном коде.

## CI/CD

`.github/workflows/deploy.yml` на каждый push и pull request в `main` гоняет
ruff, mypy и pytest, затем собирает Docker-образ. При пуше непосредственно в
`main` (не на pull request) следом идёт автодеплой на боевой сервер по SSH:
`git pull`, пересборка образа, миграции и сборка статики через одноразовый
контейнер (ещё до переключения трафика — старая версия продолжает работать,
пока не применится новая схема БД), затем `up -d --wait` дожидается, пока
`web`-контейнер пройдёт healthcheck, и только после этого перезапускается
nginx. Если миграция упадёт — деплой останавливается раньше, чем боевой
контейнер переключится на новый код.

## Резервные копии базы

`scripts/backup_db.sh` делает `pg_dump` через `docker compose exec` в
`./backups/` (gzip, имя с датой и временем), старые дампы старше 14 дней
удаляются автоматически. Каталог `backups/` не в git.

На сервере запускается по cron из корня проекта, раз в сутки:

```cron
0 3 * * * cd /opt/promo_draw && ./scripts/backup_db.sh >> /var/log/promo_draw_backup.log 2>&1
```

Восстановление — `gunzip -c backups/<файл>.sql.gz | docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"`.

Это защищает от испорченной миграции, случайного удаления и багов в коде —
не от потери самого диска сервера (бэкап лежит на нём же).
